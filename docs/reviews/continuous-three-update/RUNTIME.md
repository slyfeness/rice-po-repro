# Explicit continuation and acceleration entry

Continuation is a new run, not `--resume` on an altered parent configuration. Start from the exact private recorded parent configuration/deployment; change only the additional update budget (`total_updates=2`), output/cache directories, content-identical prompt location, and optional gradient-comparison diagnostic. Set `parent_run_root`, `parent_source_root` (the immutable original execution checkout), and `continuation_schedule_path`. All other scientific values, source assets, behavior and retrieval identities must match. The two `*_continue_two.json` templates stay execution-disabled and have unresolved local paths.

The immutable schedule JSON has `global_start=1`, `root_seed=42`, the frozen train manifest SHA-256, and `batches`: the exact ordered identities returned by `scheduled_queries(train,42,global_index,4)` at indices 1 and 2. Generate and verify it inside an authorized Slurm CPU job before submission; both methods bind the same file hash. Query/trajectory seeds use global positions; local receipt/checkpoint directories remain iterations 0 and 1. Final optimizer steps are 2 and 3 for the frozen single-step PPO plan.

`parent_run` verifies the complete published parent checkpoint, actual original package files, bound metadata and development selection. The child loads its actor, optimizer and CPU/CUDA RNG, while loading its fixed reference from the original initial-model asset. Source changes are recorded as a child source identity, never presented as the parent identity. `loaded-state.json` records the restored step and RNG probes. Parent files are read only. Child `--resume` retains the existing strict checkpoint-only recovery rule and does not replay an ambiguously committed optimizer step.

With the frozen cadence of 3, global update 2 saves a checkpoint without an intermediate development scan; global update 3 evaluates all 32 queries. The parent update-one evaluation remains unchanged. `selected_checkpoint` is local for existing recovery, while `lineage_selected_checkpoint` additionally compares the parent's precommitted development selection (earlier wins ties). Formal test selection for such lineages explicitly rejects until that interface is supported; this task evaluates development only.

The existing `serial_hf_v1` backend remains default. `hf_native_wavefront_v1` explicitly opts into batch generation: four originals per query, five branches per anchor, independent per-request generators, and native histories through the common rollout transition. Think and Summary budgets sum to the same 4096 model tokens. Deterministic Summary opener/role/tool tokens remain context with no direct action loss. Batch KV state is local to one stage invocation; it does not survive a weight update. Captured sampled log probabilities remain the PPO denominator and are checked against full-history teacher forcing before any optimizer update.

Source integration alone does not qualify a batch experiment. The original serial continuations use immutable release `e70e6b2`; GRPO completes from that release. After a native-token decoder failure, RICE continues in a separate recovery run using `534b853` (see `RECOVERY.md`), retaining the same sampler and scientific values. The independent batch workload uses `1f42d2b`; the actual-weight-switch gate uses `534b853`. Later checks do not alter a running release. Results state actual lengths, probability errors, failed actions and workload costs; short or failed tests do not qualify unseen longer histories. A fresh run is needed when enabling a different sampler backend. No vLLM or four-rank FSDP support is implied.

Independent checkpoint verification accepts `--iteration` (local, default 0), uses the run's exact immutable package source and checks global optimizer position, actual actor/optimizer state and CPU/CUDA draws. It never performs an optimizer step. All cluster commands require Slurm, offline assets and private bulk storage. No automatic job submission, downloads or CI were added.
