# Measured basis for future capacity planning

This is planning evidence, not authorization or a promise that a specific GPU topology can run the paper experiment.

The frozen single-process path uses two devices, with FP32 Actor plus fixed Reference on the actor device and BF16 Diver on the second. Two independent two-device allocations allow RICE/GRPO to overlap; this is not a four-device single-update speedup. Final Slurm accounting includes initialization, all failed runs, checkpoint I/O and independent verification. Allocator peaks and wall categories are in `EVIDENCE.json`, rather than an inferred utilization percentage.

The real sampling benchmark processes one fixed training query, four originals, four selected entropy anchors and twenty new counterfactual continuations. It produces 42,145 model tokens and 60 real retrieval calls in both modes, including illegal-terminal trajectories. Serial/batch generation takes 973.126/885.689 seconds; whole measured workload takes 1044.923/942.865 seconds. This is not a complete optimizer/update benchmark and its particular failure/depth distribution cannot be extrapolated as a universal per-query cost.

For a **hypothetical workload with exactly that same token/depth mix**, 128 such query workloads would require about 37.15 hours serial or 33.52 hours batch on the same two-device path, before optimization and checkpoint work. That is roughly 74.31 or 67.05 allocated GPU hours. This arithmetic is not a paper-training budget estimate: successful long branches, parallel scheduling, reference scoring, data/domain mix, failures, I/O and padding all change cost. It exceeds the earlier32 GPU-hour cap, which the user subsequently removed. The present task is still the small continuous comparison and acceleration qualification; no full128-query allocation is launched automatically.
